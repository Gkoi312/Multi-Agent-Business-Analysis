# 分析师女娲

创建的是分析师 Skill，不是人物扮演。目标是蒸馏一套可复用的分析师操作系统：这个角色如何提问、如何搜索、如何判断证据、如何处理不确定性、如何写 memo 章节。

## 核心理念

不要问“这个人怎么想”，而要问：

- 这个分析师负责改善哪类决策？
- 这个分析师信任、怀疑、拒绝哪些证据？
- 这个分析师会比别人更早追问什么问题？
- 哪些判断框架能把这个分析师和相邻角色区分开？
- 证据不足时，这个分析师必须承认什么？
- 什么样的输出契约，能让这个分析师在多 Agent 工作流里真正有用？

一个好的分析师 Skill 应该影响完整子图：

1. 提问：问出角色特有、互不重叠的问题。
2. 搜索：选择符合角色的信息源和查询方式。
3. 证据解读：区分事实、判断、推测和缺口。
4. 撰写：写出带有该分析师视角和引用纪律的章节。

## 工作流程

### Phase 0：确定分析师范围

如果用户已经指定分析师角色，直接使用。  
如果用户只给了行业或需求，推荐 2-4 个视角不同的分析师角色。

只澄清真正阻塞生成的问题：

- 行业或领域：AI、美妆、房地产、制造、金融等。
- 目标工作流：尽调、投资 memo、竞品研究、风险审查、市场地图、产品策略。
- 输出位置：独立 Skill、现有技能包、还是项目内 prompt。
- 材料模式：只用用户材料、联网调研、混合模式。

默认值：尽调工作流、中文 memo 输出、混合证据纪律，标准分析师组合为市场、技术/产品、风险合规、经营/财务。

### Phase 1：建立调研骨架

创建自包含的分析师 Skill 目录：

```text
[analyst-id]/
├── SKILL.md
└── references/
    └── research/
        ├── 01-role-boundary.md
        ├── 02-key-questions.md
        ├── 03-source-strategy.md
        ├── 04-judgment-framework.md
        ├── 05-blindspots-and-failure-modes.md
        └── 06-output-contract.md
```

如果是完整行业包，可以按宿主项目约定，创建“一个目录一个分析师”，或“一个行业包目录包含多个分析师 markdown”。

### Phase 2：六路蒸馏

先填完六份调研文件，再写最终 Skill。

| 文件 | 目的 | 必须包含 |
|---|---|---|
| `01-role-boundary.md` | 定义角色边界 | 负责什么、不负责什么、相邻角色、升级/交接条件 |
| `02-key-questions.md` | 定义提问风格 | 必问问题、追问模式、红旗问题、停止条件 |
| `03-source-strategy.md` | 定义检索行为 | 首选来源、域名提示、时效规则、来源黑名单、查询模式 |
| `04-judgment-framework.md` | 定义判断工具 | 3-7 个框架、所需证据、失效条件、应用示例 |
| `05-blindspots-and-failure-modes.md` | 定义怀疑方式 | 常见误判、漏判、过度推断、证据陷阱 |
| `06-output-contract.md` | 定义交付格式 | 必备章节、引用规则、不确定性标签、字数预算、交接格式 |

如果某个维度材料不足，必须在对应文件中明说。一个诚实但薄的分析师，比一个自信但通用的分析师更有价值。

### Phase 3：提炼分析师框架

综合前先阅读 `references/analyst-extraction-framework.md`。

一个框架只有同时通过三项测试，才能进入核心判断框架：

- 跨任务复现：适用于该领域内多个公司或场景。
- 有生成力：能帮助分析师面对新公司时提出更好的问题、搜索或判断。
- 角色区分度：尤其属于这个分析师，而不是通用尽调建议。

如果候选框架只通过一到两项，降级为决策启发式。三项都不过，丢弃。

### Phase 4：编写分析师 Skill

阅读 `references/analyst-skill-template.md`，生成最终 `SKILL.md` 或项目内 skill-card markdown。

必备章节：

- 角色使命
- 触发与边界
- 提问风格
- 搜索策略
- 证据层级
- 核心判断框架
- 决策启发式
- 盲区与反模式
- 回答纪律
- Memo 输出契约
- 多 Agent 交接规则
- 诚实边界

避免人格表演。分析师可以有清晰的专业声音，但目标是行为可靠，不是口癖或戏剧化人设。

### Phase 5：验证

阅读 `references/analyst-fidelity-scorecard.md` 并评估 Skill。

至少测试：

- 这个分析师问的问题是否不同于其他角色？
- 搜索策略是否会路由到符合角色的信息源？
- 回答是否能区分事实、判断、推测和缺口？
- Memo 章节是否遵守输出契约？
- 证据不足时是否会承认不确定，而不是编造？

对于可复用的分析师包，生成 `EVAL.md` 或 `FIDELITY.md`。

## 接入建议

对于 LangGraph 风格的尽调系统，把分析师 skill card 注入所有做推理决策的节点：

- `ask_question`：使用提问风格、盲区、关键问题。
- `generate_search_query`：使用搜索策略和证据层级。
- `generate_answer`：使用判断框架和回答纪律。
- `write_section`：使用 memo 输出契约和交接规则。

如果只能先改一个节点，优先改搜索 query 生成。更好的检索会让后续分析自然变好。
